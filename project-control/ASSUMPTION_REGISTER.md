# Assumption Register

Assumptions made when verified information was unavailable. Each assumption is reasonable, documented, reversible, and labelled as an assumption (not as fact) in downstream artifacts.

## A-001 — Canadian primary-source availability
- **Assumption:** Public Canadian primary sources (Parliament of Canada, Department of Justice, OPC, Treasury Board, ISED, CAISI, Public Safety, CSE, Library and Archives Canada, SCC, provincial legislatures and privacy regulators, CanLII) are publicly accessible via their official portals; the project references them by official title and publishing body without claiming local full-text archival storage.
- **Basis:** Public-record nature of Canadian legislative and regulatory instruments.
- **Reversibility:** If a source is later found to be paywalled or withdrawn, replace the citation with the nearest equivalent official reference and record the substitution in `DECISION_LOG.md`.

## A-002 — AIDA-style framework as policy reference
- **Assumption:** The proposed *Artificial Intelligence and Data Act* (AIDA) as introduced in Bill C-27 remains the most recent federal horizontal AI bill of record; the project cites it as proposed legislation (not enacted law) and clearly distinguishes it from current law.
- **Basis:** Public legislative record.
- **Reversibility:** If AIDA is enacted, replaced, or withdrawn, the legal report and government proposal must be updated to reflect the new state.

## A-003 — Treasury Board Directive on Automated Decision-Making (AIA)
- **Assumption:** The Treasury Board of Canada Secretariat's *Directive on Automated Decision-Making* and its Algorithmic Impact Assessment (AIA) instrument remain the operative federal administrative framework for automated decision systems in the public sector.
- **Basis:** Treasury Board public policy record.
- **Reversibility:** Updates to the Directive or AIA methodology require corresponding updates to the AIA extension proposal.

## A-004 — Ed25519 long-term cryptographic suitability
- **Assumption:** Ed25519 remains an acceptable signature scheme for a permanent-record system over the project's planning horizon (≈10 years), with documented migration paths to post-quantum schemes when standardized.
- **Basis:** NIST PQC standardization progress; Ed25519's mature analysis.
- **Reversibility:** The signing module is interface-isolated; a future scheme can be added behind the same `Signer` interface.

## A-005 — JSONL ledger scalability for reference implementation
- **Assumption:** For the reference implementation scale (single organization, demonstration workloads), append-only JSONL with hash chaining is sufficient. Production deployments will require a higher-throughput append-only store (e.g., FoundationDB, FoundationDB-style layers, or a purpose-built log-structured store).
- **Basis:** Master Prompt §21 explicitly identifies SQLite for local demonstration and PostgreSQL-compatible production design.
- **Reversibility:** The storage interface allows swapping the backend without changing the ledger semantics.

## A-006 — GitHub dual-repository evidence pattern
- **Assumption:** A dual-repository pattern (private evidence + public verification) is the right architectural pattern, with a private repository holding encrypted sensitive evidence and a public repository holding only signed Merkle roots, revocation status, certification status, and public schemas.
- **Basis:** Master Prompt §8.
- **Reversibility:** Federation can extend to additional anchors (e.g., a national archive, a transparency log) without re-architecting the core.

## A-007 — Bilingual treatment
- **Assumption:** English-primary body content with French key-term annotations and bilingual identity satisfies the bilingual presentation requirement at this stage; full French translation is documented as future work.
- **Basis:** Master Prompt §34 mandates bilingual organization identity; full bilingual body is a downstream production task.
- **Reversibility:** A full French edition can be produced as a parallel package.

## A-008 — Synthetic benchmark data
- **Assumption:** Synthetic benchmark data generated by reproducible scripts with fixed random seeds is sufficient to demonstrate functional correctness, tamper detection, and performance characteristics; it is not a substitute for field deployment data.
- **Basis:** Master Prompt §17 and §35 require synthetic data to be labelled and forbid representing it as empirical observation.
- **Reversibility:** When real deployment data becomes available, benchmarks should be re-run and results updated.

## A-009 — Autonomous validation depth
- **Assumption:** Internal independent validation by separate agent roles (A31 citation auditor, A32 engineering validator, A33 adversarial reviewer, A34 visual/document validator) satisfies the Gate 12 independent validation requirement at the project-preparation stage. External peer review is a separate, post-authorization activity.
- **Basis:** Master Prompt §0 forbids external publication; validation must therefore be internal.
- **Reversibility:** External peer review remains a precondition for external publication.

## A-010 — Context-specific Indigenous data governance engagement
- **Assumption:** Indigenous data-governance analysis is grounded in publicly available frameworks (OCAP® principles, First Nations Information Governance Centre materials, Inuit Tapiriit Kanatami and Métis National Council policy positions, TRC Calls to Action). The analysis is not a substitute for meaningful rights-holder engagement when a deployment materially affects Indigenous rights, community data, governance authority, or services. This engagement is not a universal prerequisite for unrelated implementations.
- **Basis:** Public-record frameworks.
- **Reversibility:** Engagement outcomes, where the material nexus exists, must be reflected in revised versions of the Indigenous data-governance analysis.
